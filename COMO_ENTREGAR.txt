1 — EXTRAIR E IDENTIFICAR O PROJETO

Extraia Atividade-M1-ViaCEP.zip para uma pasta no computador.
Entre em aula-2-adicionando-novos-campos-main.
Essa é a pasta que contém pom.xml, README.md, src e postman.
Abra essa pasta no IntelliJ, VS Code ou outro editor de sua preferência.
Leia o README.md para entender os endpoints e as regras da implementação.

2 — PREPARAR O COMPUTADOR

Você precisa de:
- JDK 17: https://adoptium.net/temurin/releases/?version=17
- Docker Desktop, usando containers Linux: https://www.docker.com/products/docker-desktop/
- Postman Desktop: https://www.postman.com/downloads/
- Git: https://git-scm.com/downloads
- Conta no GitHub: https://github.com/
- Internet para baixar dependências e consultar a ViaCEP.

Maven não precisa ser instalado separadamente: o projeto inclui mvnw.cmd.
Node.js é necessário apenas para os testes opcionais com simulador/Newman.

Abra um PowerShell dentro da pasta do projeto e confira:

java -version
git --version
docker --version

Se java não for encontrado, confira a instalação do JDK, JAVA_HOME e PATH.
Após instalar as ferramentas, feche e abra novamente o terminal.
As ferramentas portáteis usadas na preparação não estão incluídas no ZIP.

3 — SUBIR O BANCO E INICIAR A API

Abra o Docker Desktop e aguarde estar funcionando.
No PowerShell, dentro da pasta que contém pom.xml, execute:

docker compose up -d --wait
.\mvnw.cmd clean verify
.\mvnw.cmd spring-boot:run

O primeiro comando cria o PostgreSQL. O segundo compila e executa 27 testes
automatizados com H2 no perfil de teste. O terceiro inicia a aplicação com
PostgreSQL real. Aguarde a mensagem de inicialização da aplicação e do
servidor na porta 8080. Mantenha o terminal aberto.

Configuração local de demonstração:
- Banco: product
- Usuário: postgres
- Senha: password
- Porta do banco: 5432
- API: http://localhost:8080/product

Não é necessário executar os scripts SQL manualmente. O Flyway executa as
migrations e cadastra os produtos de exemplo na primeira inicialização.
Se já houver PostgreSQL usando a porta 5432, configure seu banco existente
ou libere essa porta antes de usar o Compose. O README explica as variáveis.

4 — TESTAR NO POSTMAN E EXPORTAR A COLLECTION

4.1 Abra o Postman Desktop e clique em Import.
4.2 Selecione:
    postman/Atividade-M1.postman_collection.json
4.3 Confira a variável da collection:
    baseUrl = http://localhost:8080
4.4 Execute a pasta "01 - CRUD e ViaCEP real" no Collection Runner.
    Use uma iteração e mantenha a ordem das 30 requisições.
    Não execute a pasta 02 sem preparar o simulador explicado no README.
4.5 Confira se as 58 verificações passaram. O ID do produto é salvo
    automaticamente pela primeira requisição; não precisa copiá-lo.
4.6 Os testes verificam CRUD, validações, filtros, top 5 e disponibilidade:
    - Mogi das Cruzes: CEP 08773380.
    - Recife: CEP 50010000.
    - Porto Alegre: CEP 90010000.
    - Mesma cidade: true.
    - Cidade diferente: false.
    - CEP inválido: HTTP 400.
    - CEP inexistente: HTTP 404.
    - Produto inexistente ou inativo: HTTP 404.
4.7 No menu da collection, escolha Export e selecione o formato v2.1.
    Salve como Atividade-M1.postman_collection.json na pasta postman do
    projeto, substituindo o arquivo importado, se necessário.
    Exporte a COLLECTION; apenas um relatório de execução não a substitui.
4.8 Se o professor solicitar evidência visual, salve uma captura dos
    resultados do Runner em docs/evidencias antes de publicar.

Para testar indisponibilidade, timeout e respostas inválidas, siga a seção
"Resiliência reproduzível" do README. Ela explica como iniciar o simulador
e a segunda instância da API e rodar a pasta 02: seis chamadas e 12
verificações adicionais. O simulador exige Node.js e não altera a ViaCEP real.
